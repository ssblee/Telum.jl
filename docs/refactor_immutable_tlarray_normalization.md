# Refactor plan: immutable TLArray normalization

## Goal

Make `TLArray` storage compatible with future lazy view objects by removing
hidden payload mutation of stored w-matrices and RMT blocks.

The target invariants are:

- Stored non-Abelian w-matrices are always isometries.
- Stored w-matrix payload arrays and RMT payload arrays are not changed in-place
  after they are part of a constructed `TLArray`.
- The public in-place normalization API is removed.
- The special rank-0 and rank-2 presentation remains close to the current text
  display, but display computes the old-looking factors instead of requiring
  special stored normalization.

This should be a minimal function-level refactor. Do not introduce new structs,
trait systems, or wrapper objects for this work.

One concrete optimization enabled by this change is cheaper singleton
insertion/deletion. `addSingleton` and `deleteSingleton` should eventually be
able to reuse the old sector w-matrices and RMT payload arrays whenever the
operation only adds/removes trivial size-1 physical axes. The current rank-2
normalization blocks that: if either the input or output rank is 2, construction
can rescale w-matrices and RMTs, so the implementation must allocate copied
numerical data to avoid corrupting the source tensor. Removing rank-special
payload normalization makes it possible to implement those singleton operations
as mostly metadata/shape transformations with shared immutable numerical
payloads.

## Important distinction

Not every constructor helper ending in `!` is equally problematic.

Acceptable constructor-local mutation:

- Reordering sector slots in `qlabels`, `wmats`, and `RMTs`.
- Resizing the `wmats` and `RMTs` vectors during zero-sector dropping.

This does not mutate the matrix payloads inside `wmats` or the data arrays inside
`RMTs`. It is therefore not the aliasing hazard that blocks future views, as long
as callers do not expect the input container order/length to be preserved.

Problematic mutation:

- Changing entries of a stored w-matrix with `wmat[:] = ...`,
  `wmat[:] .*= ...`, etc.
- Changing entries of a stored RMT with `sector_rmt(q, i)[:] = ...`,
  `RMT[:] .*= ...`, etc.

That payload mutation is the part to remove from constructor normalization and
from public APIs.

## Current behavior

Current rank-special normalization appears in three places:

- `_normalize_wmats!` in the constructor:
  - for `QD == 2`, it changes scalar non-Abelian w-matrices to `sqrt(dim)` and
    divides the sector RMT by the same factor;
  - for `QD == 0`, it changes scalar non-Abelian w-matrices to `1.0` and
    multiplies the scalar factor into the sector RMT.
- `normalize_qspace!`, a public in-place function with the same rank-0/rank-2
  normalization behavior.
- `_localspace_cgt_fields`, which pre-normalizes rank-2 local-space fields before
  building the `TLArray`.

There is also `_orient_wmats!`, which flips negative scalar w-matrices and
compensates by mutating the sector RMT. This is different from rank-special
normalization: once a `TLArray` has been constructed, its stored w-matrices are
already oriented, so running `_orient_wmats!` again on reused w-matrices from
that existing tensor should be a no-op and should not mutate those reused
payloads.

`_drop_zero_sectors!` reorders and resizes containers but does not modify the
w-matrix or RMT payload arrays. That can stay unless a later API decision
requires preserving caller-owned container order.

Current `addSingleton` and `deleteSingleton` both allocate copied RMT data.
Those copies are necessary under the current rank-special normalization when the
operation crosses rank 2, because the constructor may otherwise modify numerical
payloads that are still reachable from the original tensor.

## Desired storage model

Use one stored convention across ranks:

- W-matrices generated by decomposition are kept as isometries.
- Rank-0 and rank-2 scalar non-Abelian `1x1` w-matrices should be stored as
  isometric values, normally `1.0` after sign orientation.
- Rank-2 tensors should no longer store `sqrt(dim)` in the scalar w-matrix.
- The RMT should store the physical reduced block under this isometric-wmat
  convention.
- Sign orientation is an idempotent canonicalization. Reused w-matrices from an
  existing `TLArray` are already oriented and should not be copied or mutated
  just to pass through orientation again.
- Adding or deleting singleton physical axes should not force w-matrix/RMT
  payload copies just to protect against constructor normalization.

The physical tensor represented by a `TLArray` must not change.

## Display compatibility

The old rank-2 display effectively shows:

```julia
stored_rmt_under_old_normalization    sqrt(cgt_size)
```

After switching storage to isometric w-matrices, the stored rank-2 RMT contains
the old display scalar multiplied by `sqrt(cgt_size)`. To keep display similar,
compute the displayed scalar on the fly:

```julia
display_rmt = only(sector_rmt(q, sector).data) / sqrt(_sector_cgt_size_2d(q, sector))
```

for scalar rank-2 RMT sectors, then keep printing the trailing
`sqrt(_sector_cgt_size_2d(q, sector))` marker.

Rank-0 display should continue to print the effective scalar from `q[]`. With
canonical isometric w-matrices, no separate display factor is needed.

## Phase 1: remove explicit public normalization

Delete or deprecate `normalize_qspace!`.

Do not add a replacement mutating API. If a non-mutating normalization helper is
needed for migration or tests, it should return a new `TLArray`.

Expected internal cleanup:

- Remove calls to `normalize_qspace!`, if any.
- Remove comments that describe rank-2 storage as `wmat[1,1] = sqrt(dim)`.
- Rename any remaining `qspace` normalization terminology only when touching the
  relevant function; avoid a broad unrelated rename.

## Phase 2: remove local-space pre-normalization

Remove the rank-2 block in `_localspace_cgt_fields` that mutates
`sector_wmats[i]` and `RMT`.

The SVD-produced w-matrices should remain isometries. If rank-2 display should
look like the old output, display should compute that presentation factor rather
than storing it in the w-matrix.

Keep the sign-orientation logic separate from the rank-2 `sqrt(dim)`
normalization. Existing `TLArray` w-matrices are already oriented, so reusing
them in a new tensor should not trigger mutation. If raw newly produced
w-matrices are not oriented yet, orient them before they become shared storage.

## Phase 3: replace constructor rank-special payload normalization

Remove the `QD == 2` branch of `_normalize_wmats!`.

For `QD == 0`, the current behavior makes scalar w-matrices isometric by
absorbing their factors into the scalar RMT. That transformation is idempotent,
but it still mutates payload arrays after `new`. Prefer replacing it with a
pre-construction helper that prepares the RMT and w-matrices before storage.

Suggested minimal helper shape:

```julia
_canonicalize_scalar_wmats(symm, qlabels, wmats, RMTs, ::Val{QD})
```

Rules:

- For `QD == 2`, do not multiply w-matrices by `sqrt(dim)`.
- For `QD == 0`, absorb any scalar w-matrix value into a fresh scalar RMT and
  store a fresh `1x1` isometric w-matrix if the input value was not already
  `1.0`.
- For all ranks, orientation is only active for newly produced or externally
  supplied unoriented scalar `1x1` w-matrices. Reused w-matrices from an existing
  `TLArray` are already oriented, so this step must be a no-op for them.
- If a sector already satisfies the canonical convention, reuse its existing
  matrix/RMT payloads.

This keeps the optimization local: allocate only for sectors that need scalar
factor or sign absorption.

## Phase 4: adjust norm and zero-sector logic

Rank-2 stored RMTs will change meaning once the `sqrt(dim)` factor is no longer
stored in the w-matrix and no longer divided out of the RMT.

Update these together:

- `_sector_norm_sq`
- `LinearAlgebra.norm(q::TLArray{T,2})`
- any direct rank-2 use of `sector_rmt(q, i).data` that assumes old normalized
  storage

Under the new isometric-wmat convention, rank-2 physical norm should be computed
from the stored RMT data directly. Do not multiply by `_sector_cgt_size_2d`
again if that factor is already represented in the stored RMT.

## Phase 5: adjust rank-2 display

Update the scalar-width and scalar-printing sections of `Base.show`:

- For non-rank-2 tensors, keep using `_fmt_scalar_str(only(rmt.data))`.
- For rank-2 scalar RMT sectors, use a helper such as:

```julia
_display_scalar_rmt(q::TLArray, sector_index::Int)
```

which divides the stored scalar by `sqrt(_sector_cgt_size_2d(q, sector_index))`.

Keep printing the existing trailing `sqrt(cgt_size)` marker for rank-2 sectors.
This is only a display compatibility trick; it should not feed back into storage
or arithmetic.

## Phase 6: audit payload mutation after construction

Search for payload mutation patterns:

- `sector_rmt(q, ... )[:]`
- `q.RMTs[...]...[:]`
- `sector_wmat(q, ... )[:]`
- `q.wmats[...]...[:]`
- `normalize_qspace!`
- `_normalize_wmats!`
- `_orient_wmats!`

Classify each result:

- If it mutates a newly allocated output before constructing a `TLArray`, it is
  acceptable.
- If it is `_orient_wmats!` on reused w-matrices from an existing `TLArray`, it
  should be a no-op because those w-matrices are already oriented.
- If another path mutates an existing constructed `TLArray`, replace it with
  construction of a new output tensor.
- If it mutates constructor-owned temporary arrays, keep it only when there is no
  aliasing path from an existing `TLArray`.

This audit should stay narrow. Do not refactor unrelated contraction logic while
changing normalization storage.

## Phase 7: enable singleton payload reuse

After rank-special constructor normalization is removed, revisit `addSingleton`
and `deleteSingleton`.

Target behavior:

- Reuse old sector w-matrix payload arrays directly.
- Reuse old sector RMT payload arrays when adding/removing singleton axes can be
  represented by a reshape-like view or by storing the same data under the new
  `LurTensor` rank without changing numerical entries.
- Allocate only when the storage representation requires a real copied array, not
  because constructor normalization might mutate shared payloads.

Important cases:

- `QD == 2 -> QD == 3` through `addSingleton` should not rescale RMTs.
- `QD == 3 -> QD == 2` through `deleteSingleton` should not rescale RMTs.
- Appending/deleting singleton legs away from rank 2 should also preserve payload
  sharing where the `LurTensor` representation permits it.

This phase should come after the normalization refactor, not before. Otherwise
shared payloads would still be vulnerable to the constructor's rank-2
normalization path.

## Tests

Add focused regression tests because storage values and display behavior change.

Required tests:

- Rank-2 w-matrices constructed through local-space paths are isometric, not
  `sqrt(dim)`.
- Rank-2 display remains close to the old scalar-plus-`sqrt(cgt_size)` display.
- Rank-2 norm matches the old physical norm.
- Rank-0 scalar value `q[]` matches the old effective value.
- `normalize_qspace!` is no longer available, or its replacement is
  non-mutating.
- Constructor sign orientation is a no-op for already-oriented payload arrays
  reused from an existing `TLArray`.
- `addSingleton` and `deleteSingleton` crossing rank 2 do not rescale the old
  sector numerical payloads.
- Once singleton payload reuse is implemented, mutating a test copy of the source
  payload should make aliasing expectations explicit: shared immutable payloads
  are allowed internally, but no `TLArray` operation may mutate them in-place.

If testing constructor aliasing directly, distinguish container mutation from
payload mutation:

- It is okay for `_drop_zero_sectors!` to reorder/resize constructor input
  containers.
- It is not okay for constructor normalization to change the entries of a
  matrix/RMT payload that is also reachable from another constructed tensor.

Prefer adding these to an existing TLArray test file. Add a new test file only if
there is no existing constructor/display invariant test file.

## Validation

Minimum validation:

- Run the focused TLArray constructor/display tests.
- Run relevant contraction, fusion, block matching, and RMT tests.
- Run the DMRG test from `Telum/example/DMRG_central.jl`; final energies should
  remain:
  - `Nkeep=20`: `-82.37493703992092`
  - `Nkeep=50`: `-82.39703156828021`
- Inspect type stability around any new helper and contraction entry points with
  `@code_warntype` or JET if available.
- Measure allocations for representative constructor calls before and after.

Expected allocation behavior:

- Removing rank-2 normalization should reduce constructor work.
- Scalar/sign canonicalization may allocate for affected rank-0 or newly
  produced unoriented sectors. It should not allocate for already-oriented
  w-matrices reused from an existing `TLArray`.
- Future views can safely share immutable payload arrays once post-construction
  payload mutation is removed.

## Risks

- Direct rank-2 uses of raw `sector_rmt(q, i).data` may assume the old
  divided-by-`sqrt(dim)` storage. Those call sites must be audited.
- Updating display without updating norm/zero-sector logic would create
  inconsistent behavior.
- Removing `_localspace_cgt_fields` rank-2 normalization changes raw RMT storage
  values. Tests should compare physical tensor behavior, not old raw storage.
- `_normalize_wmats!` is idempotent in some cases, but idempotence does not make
  payload mutation safe for shared future view storage.
- `_orient_wmats!` should be idempotent for constructed `TLArray` storage. The
  singleton reuse plan relies on that: reused w-matrices from an existing
  `TLArray` must already be oriented and must not be modified by orientation.
- Singleton payload reuse is only safe after all constructor paths stop
  rank-special numerical rescaling. Implementing reuse first would risk source
  tensor corruption.

## Completion criteria

The refactor is complete when:

- Rank-2 storage no longer puts `sqrt(dim)` into scalar w-matrices.
- Stored non-Abelian w-matrices are isometries.
- `normalize_qspace!` is removed or replaced by a non-mutating API.
- `_localspace_cgt_fields` no longer performs rank-2 display normalization in
  storage.
- Rank-special normalization does not mutate constructed tensor payload arrays.
- Orientation remains idempotent: already-oriented w-matrices reused from an
  existing `TLArray` are not mutated.
- `addSingleton` and `deleteSingleton` can be optimized to avoid numerical
  payload copies when they only add/remove trivial singleton axes.
- 0D and 2D text display remains user-compatible with the old presentation.
- DMRG energies and relevant TLArray/contraction tests pass.
